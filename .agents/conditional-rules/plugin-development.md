# 割引プラグインの開発

## 読取と実装の順序

1. `docs/SSoT/README.md` の読み順から対象仕様を確認する。`OPEN_QUESTIONS.md` の未決が実装対象を左右するときは、その判断を解消してから該当箇所を実装する。
2. 対象 Welcart 版の実コードで、採用する関数・フック・フィルタの引数、呼出し時点、再計算、保存先を確認する。正本と確認状況は `docs/SSoT/INTEGRATIONS.md` に残す。
3. 影響する現行画面をローカルで確認し、管理画面と購入経路の UI 案を可視化してから表示の詳細を確定する。資料は `visdoc` を使い、確定した振る舞いだけを機能仕様へ反映する。

## TDD と品質確認

- 振る舞いを変える単位で、成立すべき結果のテストを先に追加し、失敗を確認してから最小限の実装、成功確認、整理を行う。テストはリポジトリ内の `tests/` に置き、既存の PHPUnit 構成を使う。
- 計算処理のテストと Welcart の連携確認を区別する。単体テストだけでカート・購入確認・受注保存の整合を証明したと扱わない。
- 設定入力・金額の境界値・保存保護は、`FUNCTIONAL_SPEC.md` の受入条件に対応する失敗ケースも確認する。
- 品質検査は `TECH_STACK_AND_OPERATIONS.md` と root `README.md` の標準入口を使う。`quality` の runner 起動・設定読込みと、割引機能テストの実行を区別し、実際にテストを走らせたコマンドと結果を残す。
- WPCS は PHPCS／WordPressCS の結果で判定する。未実行・失敗・警告・対象外を成功へ読み替えない。

## 連携記録と提出

- 本プラグインが使用する既存関数・フック・フィルタを全件列挙し、用途、採用理由、参照 URL、対象版のソース位置を `INTEGRATIONS.md` に残す。検討候補・不採用と実際の利用を区別する。
- 税、決済へ渡す金額、メール、購入履歴などの影響経路を調べ、追加改修が要る箇所と既存経路で整合する箇所を検証する。
- コマンド／操作、終了コード、期待値と実測値、対象版、画面記録を残す。外部決済・メールの実送信を検証の前提にせず、ローカル環境の既定境界を守る。
- 提出物の種類は `ASSIGNMENT_REQUIREMENTS.md` を参照し、フックの選定理由、AI 出力の誤りの発見・修正と未完成部分を追跡できるようにする。
