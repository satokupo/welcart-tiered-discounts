# 受注編集は税計算と再計算入口だけ native へ委ねる

決定日: 2026-09-08

## 決定

税額と丸めは Welcart の `getTax` / `usces_internal_tax` に委ね、再計算ボタンは標準・軽減税率の既存 script filter から署名付きプレビューへ接続する。受注全体の集計、割引配分、注文時設定、未保存明細、署名、保存保護は既存のプラグイン処理を維持する。

## 根拠

[Issue #7](https://github.com/satokupo/welcart-tiered-discounts/issues/7) と [計画 #8](https://github.com/satokupo/welcart-tiered-discounts/issues/8) に基づき、Welcart 2.12.1.2608181 の実コードと専用環境 E で比較する。ユーザーは実装着手時に、有益な代替の採用と不利な代替の見送り、commit/push、未マージを明示した。計画段階の実験と採用の分離は、この追加指示の範囲で同一作業にまとめる。

`OrderHookReplacementTest` は実物の受注再計算を呼び、標準外税では小計10,000円・割引500円から税950円・合計10,450円を得る。一方、標準6,000円と軽減4,000円では割引総額だけを渡すと税920円となり、税率別割引300円/200円も渡して初めて税874円になる。追加明細の一時IDを渡すと軽減税率の小計を取得できず、同じ税額にならない。native JSON 応答には調整後の使用ポイントも含まれず、応答終了の封じ込めも要る。

受注全体の置換は、署名付き未保存明細と注文時税区分を維持するための橋渡しを増やす。対して税率別の対象額を既存の税APIへ渡す方法なら、数式の重複を除き、native option を `finally` で戻すだけで済む。割引対象の登録価格を税抜価格へ変換しない。

## 境界

受注全体の native API があらゆる方法で利用不能だとは結論しない。今回試した既存入力・filter の範囲では、全面置換の保守上の利点がないという採否である。本体・テーマ、DB schema、購入時の接続は変更しない。正式な採用一覧は [INTEGRATIONS](../../../INTEGRATIONS.md) を正本とする。
