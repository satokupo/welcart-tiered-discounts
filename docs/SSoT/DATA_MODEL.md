# データモデル

## 確定している情報構造

店舗共通の割引設定 1 組が、複数のティアを持つ。MVP では全商品が対象となる。将来の対象選択とティアの計算条件を分離できる構造にする。

| 情報 | 必須内容 | 関係 |
|---|---|---|
| 割引設定 | ティア一覧、全商品を対象とする範囲 | 1 店舗に 1 組 |
| ティア | しきい値金額、方式（固定額／割合）、割引値、有効／無効 | 割引設定に複数所属 |
| 購入時の割引設定と結果 | 注文時のティア一覧全体、対象小計、適用条件、割引結果 | Welcart の注文と対応し、後日の店舗設定から独立する |
| 元注文と変更履歴 | 元の商品・数量・価格・金額、保存済み編集の前後値・日時・操作管理者 | 編集時の再計算結果を追跡する。現在の請求額の正本は既存受注列 |

入力値の許容範囲、表示順、注文確定後と管理者編集時の金額の扱いは [機能仕様](FUNCTIONAL_SPEC.md) が正本。

## 保存方式

WordPress Options API の単一オプションに店舗共通の割引設定を保存する方式を、2026-09-07 のユーザー回答で採用した。オプション名は `welcart_tiered_discounts` とする。次は採用方式と入力制約を具体化した MVP の保存構造。入力表示と内部保存の単位を区別する。

| キー | 値の形 | 用途 |
|---|---|---|
| `schema_version` | 整数 `1` | 後続の構造変更を識別する |
| `target.mode` | `all` | MVP で実際に使用する対象指定 |
| `tiers` | ティアの配列 | 店舗共通の設定一覧 |
| `tiers[].threshold` | 円単位の整数 | 適用しきい値 |
| `tiers[].type` | `fixed` / `percentage` | 固定額／割合 |
| `tiers[].value` | 正の整数 | `fixed` は円額。`percentage` はパーセントの 100 倍（10.25% → 1025、100% → 10000） |
| `tiers[].enabled` | 真偽値 | 有効／無効 |

割合は小数の丸め誤差を避けるため整数で保存し、計算時は `floor(S × value / 10000)` とする。金額上限と中間計算のオーバーフロー回避は対象 PHP・Welcart との実測事項として残す。

初期値は `schema_version=1`、`target.mode=all`、`tiers=[]`。検証済みの一覧全体を保存し、手動並び順の専用項目は設けない。設定が存在しない状態と保存済みデータの破損は区別する。破損時の注文停止・通知・内部ログは [機能仕様](FUNCTIONAL_SPEC.md) に従う。

カテゴリ一覧・会員ランク・未使用の汎用条件を先行追加しない。`target` は MVP では全商品で固定し、将来の対象指定単位まで確定したものではない。

[WordPress Options API](https://developer.wordpress.org/apis/options/) は設定データの保存・取得・更新を扱い、[Settings API](https://developer.wordpress.org/plugins/settings/settings-api/) は設定画面と保存処理を構成するための標準機能である。店舗共通の小さな設定という現在の要件に合うため採用する。

## タクソノミー案との関係

カスタムタクソノミーとしてキャンペーンを作り、商品へ紐づける案は、今回の保存方式としては採用しない。MVP は店舗共通の 1 組・全商品対象であり、新しい分類と商品との紐づけを管理する必要がないため。割引設定の保存方式と、既存の商品カテゴリを使った対象選択は別の判断である。

将来の対象指定を一覧全体で共通にするか、ティアごとに持たせるかは未決。いずれの場合も、対象小計を作る処理とティアを選択・計算する処理を分け、全商品対象の MVP をカテゴリ機能の先行実装へ広げない。後続の対象選択の意味は [後続機能](../work/todo/POST_MVP.md) に保持する。

## アクセスとデータの境界

確定した受注と割引結果を対応させ、後日の設定変更から独立して過去の金額を維持する。注文時の検証済み設定（全ティアのしきい値・方式・値・有効状態）、店舗の価格税区分、商品・SKU・数量・減額前の基準価格、対象小計、適用条件、割引結果を注文時点の情報として追跡できる構成にする。注文全体に 1 回の割引を、商品ごとの固定額として保存しない。

既存の Welcart 保存項目を利用し、当時の再計算に必要なティア一覧全体と元注文・変更履歴などの不足情報だけを注文のメタ情報等へ保存する。管理者が変更した明細の基準価格を使って再計算し、プレビュー値は保存まで現在受注と区別する。保存時に前後値・日時・操作管理者を追記し、注文時の設定・元注文・過去履歴を上書きしない。履歴中の金額は過去の証跡であり、現在請求額の正本として使わない。二重の請求額正本や新しい受注テーブルは作らない。物理的な保存先・拡張 hook・復元経路は対象版の調査で確定し、`INTEGRATIONS.md` へ記録する。受注画面・メール・履歴を現行の割引設定から再計算しない。

- 割引設定の変更は権限を持つ店舗管理者に限り、capability は `manage_options` とする。
- 購入者へ設定変更権限や他の購入者の注文情報を公開しない。フロント表示は購入に必要な適用条件・割引結果を対象とする。
- WordPress／Welcart の内部テーブルを推測で更新する方式を採らず、確認した既存 API・拡張経路に沿って連携する。
- 保存先、取得時点、計算結果の受渡し、受注との対応を [連携資料](INTEGRATIONS.md) から追跡可能にする。
