# SSoT 索引（正本）

このフォルダ（`docs/SSoT/`）は、このリポジトリの **仕様・設計の正本（SSoT: Source of Truth）** を置く場所。複数の資料で言っていることが食い違ったとき、ここに書いてあるほうを正とする。

本書は **AI が必要時に開く索引**（毎回自動で読まれるのは `AGENTS.md` と `CLAUDE.md` のみ）。SSoT 配下を扱う作業の前に、本書の文書マップで読むべき文書を判定する。

## 何をここに置き、何を置かないか

| 置く | 置かない（行き先） |
|---|---|
| 何を作るか（仕様） | 一般の操作手順 → `docs/` 配下・各 `README.md`（ローカル開発の手順は `LOCAL_DEVELOPMENT.md` に集約） |
| どういう構造で作るか（設計） | どの順で進めるか → `docs/work/MILESTONES.md` |
| なぜそう決めたか → `decisions/`（索引は `DECISIONS.md`） | 次に何をするか → `docs/work/todo/` |
| | やったことと判断・変更の履歴 → `docs/work/log/` |
| | AI への行動指示 → `AGENTS.md` |

**ここに置くのは「確定した内容」、または基本的に確定扱いで書き換えない内容だけ**。

**「今はこう」というタイミングを含むものを置いてはならない。** 仕様文書は現在形だけを書く場所であり、書いた瞬間のタイミングを含めると、誰も更新しないまま古い状態が正本として引用され続ける。進捗・段取り・作業状況は `docs/work/` 側が持つ。

**唯一の例外が `decisions/`。** ここだけは時間軸を持つ（年月フォルダ・日付入りのファイル名・失効した決定も消さずに残す）。仕様文書が「今どうなっているか」を書くのに対し、判断ログは「なぜそうなったか」を時系列で残すためにあり、役割が違うので同居してよい。**この例外を `decisions/` の外へ広げない。** 進捗・作業状況を「履歴だから」と SSoT に置く根拠にはならない。

上の表で「判断」が両側に出てくるのは、行き先が2つに分かれるため。後から**仕様の根拠**として引かれるなら `decisions/`、**作業の経過**として追われるなら `docs/work/log/`。

## 構成要素の役割分担

| ファイル | 役割 | 読まれ方 |
|---|---|---|
| `README.md`（本書） | 索引の正本（文書マップ・判定表・手順・命名ルール） | 必要時に開く |
| `AGENTS.md` | このフォルダを触るとき毎回認識すべき運用ルール本体 | 毎回自動（全ランタイム） |
| `CLAUDE.md` | Claude Code 向けアダプタ（`@AGENTS.md` を読み込むだけ） | 毎回自動（Claude Code） |
| `DECISIONS.md` | 判断ログの**索引**（見出しだけ。末尾追記のみ。例外は上書き時の行末追記） | 必要時に開く |
| `decisions/YYYY/MM/` | 判断ログの**実体**（1決定＝1ファイル） | 索引から該当分だけ開く |
| その他の文書 | 仕様・設計の実体 | 必要時に開く |

**`DECISIONS.md` は索引であって、まとめではない。** 決定を横断して「結局いま何がどうなっているか」を示すのは仕様文書の側（`PRODUCT_DEFINITION.md` 等の標準文書）の役割で、本書の文書マップがその入口になる。索引に要点や要約を書き足すと、決定が増えるたびに既存行の書き換えが必要になり、「末尾追記のみ」という唯一の防御が消える。**まとめが足りないと感じたときに厚くするのは、決定ログではなく仕様文書の側。**

## 文書マップ

**並び順＝依存順**（上が決まらないと下が書けない）。各文書には初期状態で「書くための指示」が入っている。指示に従ってユーザーへ聴取し、書き終えたら指示ブロックを削除して下の状態欄を更新する。

| 文書 | 何を書くか | 状態 |
|---|---|---|
| `ASSIGNMENT_REQUIREMENTS.md` | 課題提供者から指定された条件 | 作成済み |
| `PRODUCT_DEFINITION.md` | 何のため・誰のため・どの困りごとを解消するか | 記入済み |
| `MVP_SCOPE.md` | 最初にどこまで作るか／恒久的に作らないもの | 記入済み |
| `FUNCTIONAL_SPEC.md` | 各機能がどう動くか（入力・計算・例外） | 登録価格基準・破損時・受注編集の要件を記入済み。連携・画面の実測事項は確認一覧へ分離 |
| `DATA_MODEL.md` | どんな情報をどういう形で持つか | 設定構造と注文時一覧・元注文・変更履歴を記入済み。物理保存先は実測待ち |
| `TECH_STACK_AND_OPERATIONS.md` | 何で作り、どこでどう動かすか | 作成済み |
| `LOCAL_DEVELOPMENT.md` | ローカル開発の運用方針・初回設定・起動停止・確認手順 | 作成済み |
| `INTEGRATIONS.md` | 連携契約、公式 API の用途・参照先、責務の境界 | 記入済み。公式リファレンスの事実と連携契約を記載 |
| `OPEN_QUESTIONS.md` | ユーザー確認の結果と、実装前の実測・後続機能の未決事項 | 追加回答まで反映済み。技術確認・後続詳細は残存 |
| `DECISIONS.md` | 決定の索引（実体は `decisions/YYYY/MM/`） | 運用中 |

**未着手・空欄・未掲載は「要件が存在しない」ことを意味しない**（未決・未整備を意味する）。

環境の実測結果は SSoT ではなく [`docs/ENVIRONMENT_VERIFICATION.md`](../ENVIRONMENT_VERIFICATION.md) に記録する。実測前の項目は未実行のまま保持し、成功扱いにしない。

## 状況に応じて増やす文書

下の一覧は **出発点であって閉じた一覧ではない**。載っていないものでも必要なら作ってよい。ただし作ったら文書マップに登録し、既存文書と内容が重ならないことを確認する。

| きっかけ | 文書 | 何を書くか |
|---|---|---|
| 同じものを別名で呼ぶ事故が出た | `GLOSSARY.md` | 使う語と、使わないと決めた語 |
| 画面が増えてきた | `SCREEN_FLOW.md` | 画面の一覧とつながり |
| 見た目のルールが必要になった | `UI_GUIDELINES.md` | 色・余白・部品の定義 |
| 業務の手続きを扱う | `BUSINESS_FLOW.md` | 誰が何をどの順でやるか |
| 利用者に種類がある | `ACCESS_CONTROL.md` | 誰が何を見られる・できるか |
| 外部サービスとつながる | `INTEGRATIONS.md` | 相手・やり取りする情報・失敗時の扱い |
| お金を扱う | `BILLING.md` | 料金体系・請求のタイミング |
| 複数言語に対応する | `LOCALIZATION.md` | 対応言語・翻訳の持ち方 |
| 構想段階で保留が溜まる | `OPEN_QUESTIONS.md` | まだ決まっていないことの一覧 |

## タスク別の読み順

| やること | 読む文書（順に） |
|---|---|
| 課題提供者が指定した条件を確認する | `ASSIGNMENT_REQUIREMENTS.md` |
| 「これ作るんだっけ？」の判定 | `MVP_SCOPE.md` |
| 機能を実装する | `ASSIGNMENT_REQUIREMENTS.md` → `MVP_SCOPE.md` → `FUNCTIONAL_SPEC.md` → `OPEN_QUESTIONS.md` →（データに触るなら）`DATA_MODEL.md` |
| データ構造を変える | `DATA_MODEL.md` → `FUNCTIONAL_SPEC.md`（影響の確認） |
| ローカル環境の初回設定・起動停止・接続確認 | `LOCAL_DEVELOPMENT.md` |
| 並列開発・worktree の環境割当・DB 更新 | `LOCAL_DEVELOPMENT.md` → `TECH_STACK_AND_OPERATIONS.md` →（製品データを変えるなら）`DATA_MODEL.md` |
| Welcart の連携経路を調べる・変更する | `FUNCTIONAL_SPEC.md` → `INTEGRATIONS.md` → `OPEN_QUESTIONS.md` → 対象版のソース |
| 未決事項と後続作業を確認する | `OPEN_QUESTIONS.md` → `../work/MILESTONES.md` → `../work/INDEX.md` |
| 環境構築・デプロイ | `ASSIGNMENT_REQUIREMENTS.md` → `TECH_STACK_AND_OPERATIONS.md` → `../ENVIRONMENT_VERIFICATION.md` |
| 「なぜこうなっている？」に答える | `DECISIONS.md`（索引）→ 該当する `decisions/` の個別ファイル → `PRODUCT_DEFINITION.md` |

## 書く場所の判定表

| 情報の種類 | 書く場所 |
|---|---|
| 課題提供者から指定された条件 | `ASSIGNMENT_REQUIREMENTS.md` |
| 目的・対象・解消する困りごと | `PRODUCT_DEFINITION.md` |
| 作る／作らないの線引き | `MVP_SCOPE.md` |
| 機能の振る舞い・画面・計算式・例外 | `FUNCTIONAL_SPEC.md` |
| 情報の構造・項目・つながり・アクセス制御 | `DATA_MODEL.md` |
| 技術スタック・認証・実行環境・鍵の管理方針 | `TECH_STACK_AND_OPERATIONS.md` |
| ローカル開発の運用方針・初回設定・起動停止・確認手順 | `LOCAL_DEVELOPMENT.md` |
| 既存 API の用途、参照先、候補と採用、連携根拠 | `INTEGRATIONS.md` |
| 仕様上の確認事項と解決先 | `OPEN_QUESTIONS.md` |
| 後続機能の内容・優先順・未完了作業 | `../work/todo/`・`../work/MILESTONES.md` |
| 決定とその理由 | `decisions/YYYY/MM/` に1ファイル＋`DECISIONS.md` 索引に1行 |
| AI が毎回認識すべき行動ルール | `AGENTS.md`（常時有効なものだけ） |
| 上記に当てはまらない仕様・設計 | 意味名の文書を新設して文書マップに登録 |

**同じ情報を2箇所に書かない。正本は常に1つ。**

## 文書を新しく作るときの手順

1. 既存の文書に書けないか先に確認する（内容が重ならないこと）
2. 意味名で作る（下の命名ルールに従う）
3. 文書マップに行を足す
4. 書く場所の判定表に行を足す
5. 新設の理由を判断ログに記録する（`decisions/YYYY/MM/` に1ファイル＋`DECISIONS.md` 索引に1行）

## 連動更新表

| 変更 | 連動して直すもの |
|---|---|
| SSoT 文書の追加・削除・改名・役割変更 | 本書の文書マップ・書く場所の判定表・タスク別の読み順 |
| 文書を書き終えた／大きく書き換えた | 本書の文書マップの状態欄 |
| 仕様・設計の非自明な判断 | `decisions/YYYY/MM/` に個別ファイルを作成し、`DECISIONS.md` 索引にも1行足す（**片方だけで終わらせない**） |

## 命名ルール

- 予約ファイルは `README.md`・`CLAUDE.md`・`AGENTS.md`・`DECISIONS.md` の完全一致4件（この4枚だけが運営ファイル）。予約ディレクトリは `decisions/` の1件（判断ログの実体置き場であり、仕様文書を入れない）
- 仕様文書名は内容を表す ASCII の英語による安定名にし、`UPPER_SNAKE_CASE.md` を使う。本文と見出しは日本語でよい
- 連番・日付・版番号・状態語（draft / final 等）を含めない
- 良い例: `DATA_MODEL.md` `BILLING.md` ／ 悪い例: `01_DATA_MODEL.md` `BILLING_FINAL_V2.md`
- **`decisions/` 配下だけはこの例外**。判断ログは「いつ決めたか」が内容の一部なので、`decisions/YYYY/MM/YYYY-MM-DD_タイトル.md` と日付を持つ（安定名の規則は仕様文書に対するもの）
