提出物について

本課題では、割引額の計算を共通化し、Welcartの既存フックを通じてカート、購入確認、受注保存へ接続する方針で実装しました。 Welcart本体とテーマは変更していません。 登録販売価格と数量の商品小計を基準に、条件を満たす最も高いしきい値の1段を適用します。

採用したフックと判断理由は設計メモ、3箇所の金額整合を確認した記録は動作確認にまとめています。 AI活用レポートでは、人間が仕様を判断した場面と、AIの出力をテストで再現して修正した過程を説明しています。

提出版と追加調整版

提出版をmainブランチに残し、翌日の追加検証と調整を含むdevブランチが少し先行する形で管理しています。

  • 提出版（main）：想定作業時間を超えた段階で、実行中だったAIの一括処理の完了を待ち、最後に簡易的な全体レビューと必要な修正を行って作業を止めた版です。今回の主たる提出対象です。
  • 翌日の追加調整版（dev）：mainをもとに、翌日改めて検証し、内部処理の2箇所をWelcartの既存機能を使う形に寄せた参考版です。

調整したのは、税額計算をWelcartの既存関数へ委ねる部分と、受注画面の再計算ボタンを既存フィルタから接続する部分です。 あわせて、前日に未確認だったWordPressの下限環境と最新環境で、購入から受注保存までの追加検証を行いました。

提供する機能と画面上の操作は、mainとdevで共通です。 devは内部実装を調整したもので、利用者から見える動きは変えていません。 2箇所の調整内容と採用理由は、設計メモに記載しています。

開発後に整理した設計のまとめ

以下は、開発を終えた後に、AIとのブレストで検討した内容と実装結果を通して整理したものです。 採用したフックとその理由、見送った候補、翌日に見直した点をまとめています。

設計の要点

割引額を計算する処理を共通化し、Welcartの計算・表示・保存の流れへ接続しました。 Welcart本体・テーマのファイルは変更していません。

設定保存にはWordPress Settings APIを使い、manage_optionsによる権限確認、標準nonceの検証、入力値の検証・サニタイズを行います。不正入力では既存設定を保持します。

受注編集では、購入時に有効だった全ティアを保存し、店舗側の管理者による受注編集時にも購入時点のレートで再計算可能にしています。再計算結果は保存時にもサーバーで照合し、金額と履歴の書込みに失敗した場合はDB更新を巻き戻します。

以下は、AIが技術的な採否を整理したものです。私が説明を受けて判断した経緯は、AI活用レポートの「AIの提案に対して人間が判断したこと」に記載しています。

課題の必須要件を超えて含めた範囲と理由

課題で求められていたのは、カート・購入確認・確定後の受注データで割引結果を整合させるところまででした。ただ、実際の店舗業務を想像すると、注文後に在庫状況などによって数量を変更することは十分にありそうだと考えました。そのため、既存の受注編集でも割引を適切に扱えるようにした方がよいと判断し、今回の作業に含めました。

これに伴い、変更後の明細による再計算、購入時のティアの保存、保存前の計算結果の確認など、一連の関連処理も必要になりました。実際の業務を想定すれば、受注編集への対応は今も必要だったと考えています。ただし、変更履歴の保持まで含める必要があったかは、振り返ると見直す余地があったと考えています。

割引方式は、固定額に加えて割合も選べるようにしました。課題では固定額だけで割引するよう指定されておらず、実際の運営では割合で割引したい店舗経営者もいるだろうと考えたためです。また、当時は固定額か割合かという計算方法の違いであれば、ロジックの変更も大きくないだろうと見込み、今回の実装に含めました。

実務を想定して範囲を広げた結果、設計・実装・検証の対象も増え、全体では想定の5〜7時間を超えました。個々の対応には理由がありましたが、課題としてまず満たす範囲と、その後に対応する範囲を、時間の制約に合わせて切り分けきれなかった点は反省しています。

AI活用レポート

要求整理・UI検討・詳細計画（約5時間）

AIと人間の認識合わせをするパートです。ブレストを重ねるとだんだん情報が複雑になるので、大まかな枠組みを理解するのに適したELI5スキルを併用しています。

1. 要求のブレストと作業フレーム

必須要件をベースに、ブラウザ版ChatGPT Proと、どのようなプラグインにするかを大まかにブレストします。これを「作業フレーム」（要求定義相当）としてIssueにまとめ、ローカルのCodexと認識を共有します。

2. 実画面をもとにしたUI案の作成と調整

ローカル環境は、事前にWelcartの推奨動作環境と最低動作環境をAIに確認させ、Docker Desktopを利用して構築しています。

その環境内でCodexに作業フレームを提供し、関連するページを特定して、Welcart入りの初期状態のスクリーンショットを撮影します。その素材をもとに、フレームに書かれた機能を実装する場合のUIサンプルを画像生成スキルで視覚化し、比較資料を作成します。その資料をもとにブレストを行い、作業フレームをより明確にします。

このとき、Welcartのデフォルト構造に想定外の点がいくつかあったため、フレームの修正が起きています。

3. 詳細計画の作成

確定した作業フレームをもとに、ローカルのCodexに詳細計画を作成させます。サンプルコードを書くのではなく、どの既存機能や部品を使い、どのような手順で機能を組み立てるかという、実装までの道順を具体化するものです。

これは認知負荷が高いため、人間は詳細チェックを行っていません。作業フレームをアンカーとし、目的や制約を必要十分にカバーできているかを自己チェックさせる修正ループを回します。変更が必要と判断されるたびにバージョンを上げています。旧バージョンはすべて資料として残すため、後から確認できます。

ローカル側で問題ないと判断したあとは、別のエージェントによるレビューと修正を続けます。今回はブラウザ版ChatGPT Proに外部レビューを依頼しています。

今回はローカルの自己レビュー中に、必要以上に詳細化する方向へ挙動が傾いたため、通常よりもレビューに時間がかかったことが反省点の一つです。

AIによる実装の一括実行（約2時間30分）

詳細計画を記載したIssueをもとに、worktreeの中でCodexの/goalコマンドを使い、実装・検証から実装後の自己チェックと軽微な修正のループまでをまとめて依頼します。TDDで動作テストを先に構築し、エッジケースへの対応も想定した実装を進める方式です。ローカル環境での動作確認やコーディング規約の検査も、この工程に含まれています。

Welcartの既存フックのチェックを計画書作成初期に行いましたが、実装中に改めて行うように明示的指示として含めるのが漏れてしまった点は反省点として認識しています。

実装後の簡易全体レビュー（約30分）

実装後は、ブラウザ版ChatGPT Proに実装後のワークツリーリポジトリ・作業フレーム・作業計画を読ませ、簡易的な全体レビューを行いました。 ここで見つかった割合設定の不具合は、当初は軽微と捉えていましたが、修正範囲が局所的でも割引額への影響は大きいものでした。 CodexにTDDでの再現と修正を依頼し、リポジトリ全体の調査時間も合わせて約30分かけています。 提出版のmainには、この修正までを含めています。

AIの誤りをどう発見し、修正したか

実装が一度ですべてうまくいくとは考えていないため、まず実装を担当したAI自身にレビューと修正をさせています。実装時の文脈と「本来どうするべきだったか」という計画の意図を持ったまま見直せるので、計画に含まれていたのに実装されていない項目などを、この段階で拾う狙いです。

ただし、同じAIだけでは、自分の実装を正しいと捉える確証バイアスのような偏りが残る可能性もあります。そのため、別のモデルによるレビューを重視しており、Codexで実装したものをClaudeやGrokにレビューさせる方法も使っています。

今回は、ブラウザ版ChatGPT Proをレビュー役に選びました。私の利用経験では、複雑な前提を整理して推論する場面で、コーディングに特化したCodexよりも頼れると感じることがあります。また、Codexとは異なる実行環境やツール構成でレビューすることで、同じOpenAIのモデルでも実装時とは異なる視点を得られると期待したものです。

今回のレビューで見つかった問題と修正

具体例は、初回や空の一覧から割合設定を保存するときに変換処理が重複し、0.5%が50%になるなどの不具合です。 別チャットのレビューAIによる指摘を受け、私はTDDで局所修正する範囲を指定しました。 Codexが実HTTPの保存テストで問題を再現したうえで、入力値を二重に変換しない処理へ修正しています。

修正後は、商品小計10,000円に0.5%を設定すると割引50円、10%なら割引1,000円になることに加え、再表示と再保存でも値が変わらないことを確認しました。 対象のHTTP保存テストは修正前に4件失敗し、修正後は5 tests / 85 assertionsで成功しました。 その後、全体の回帰テストも成功しています。修正記録

AIの提案に対して人間が判断したこと

AIの説明や提案を受けて、私が変更や対象外の判断をした例です。 当時の回答は、Issue #3の追加回答の記録に詳細がまとめられています。

受注編集時の割引を自動計算し、購入時の条件を保つ

当初、受注編集時に店舗側の管理者が手動で割引額を調整する案を提案されました。しかし、商品や数量を変更するたびに管理者が割引額を計算する運用は使い勝手がよくないと考え、変更後の内容に応じて自動計算する仕組みを求めました。

検討の中では、購入後に店舗のティア設定が変更されていた場合、どの条件で再計算するかという問題も挙がりました。そこで、購入時に有効だった全ティアを注文データに保存し、受注編集でも当時のしきい値と割引率・割引額で再計算するルールにしました。計算結果は管理者が確認して保存します。

Welcartの価格の扱いを確認し、登録価格をそのまま使う

未確定の仕様を詰める中で、税込価格から税抜価格を逆算するなど、複雑な計算ロジックが提案されました。この時点では私自身がWelcartの価格の扱いを十分に把握していなかったため、まず仕組みを調べて報告するよう依頼しました。

その結果、商品に登録する価格は1つで、その金額を税込・税抜のどちらとして扱うかは店舗の設定で決まるとわかりました。そこで、税抜価格への換算を追加せず、もともと登録されている金額をそのまま割引の判定と計算に使う、シンプルな方針を指示しました。

他の割引との競合は対象外とし、ポイント対応の拡張余地を残す

他の割引と競合した場合の扱いも論点になりました。ただし、組み合わせごとの条件まで考慮すると複雑になるため、競合の検出や制御はMVPに含めないことにしました。MVPでは、標準ポイントによる減額も含め、割引やポイントを適用する前の対象商品小計で判定と割引計算を行います。

一方で、将来は標準ポイントで減額した後の金額を基準にできるよう、拡張性を持たせることを求めました。ポイント適用後の判定そのものは今回実装せず、後から基準額の作り方を変更できる処理構造にしています。

うまくいかなかったことと改善点

実装中にも既存フックを確認する

AIへの基本指示には、既存フックを利用する方針と参照先を含め、計画書作成初期に確認していました。ただし、実装中にも既存フックを再確認するよう明記しておらず、利用できる既存処理の見落としが残り、翌日の見直しと修正につながりました。計画時の確認に加え、実装中にも利用候補と用途、実際の挙動を検証する工程を明示する必要があったと考えています。

試行して決める余地を計画に残す

詳細計画を作成する段階で、AIの判断が、厳密に進める方向へ想定以上に傾いていました。実際には小さく実装して挙動を確かめた方が早い部分まで事前に詳細を詰めようとしたことが、計画の修正を増やした原因の一つです。

途中でこの状況に気づき、実装時に試行して決める余地を残すよう指示を加えましたが、もう少し早く気づければよかったと考えています。今回はv5まで改訂を重ねたものの、私の見立てでは、通常ならv3程度で収束させてもよい内容でした。

この経験を踏まえ、守るべき要件と確認する結果は事前に決めつつ、実現方法のどこを試行に委ねてよいかも、最初にAIと共有するよう作業フローを修正しています。

購入者側の金額表示を分かりやすくする

購入者側の画面では、商品金額や割引額、最終的な支払額をより把握しやすくするなど、UXを高める余地がまだ十分にあると考えています。

保存処理と表示機能を分けて検討する

購入時の割引条件を保持する保存処理は必要でした。一方、変更履歴の確認にはWelcart標準の操作ログを活用できるため、独自の履歴表示は省けたと考えています。

複数の変更が重なるエッジケースへの対応は見送った

動作確認の動画を撮影しているときに、購入申請後に決済が完了していない状態で、受注内容の変更と店舗の税の方針変更が重なるエッジケースが発覚しました。 設定した作業時間を超過していたため、追加の修正には進まず、今回は対応を見送りました。

対応を再開する場合は、このケースをAIに伝え、これまでと同じ流れで再現テストから修正、回帰確認までをTDDで進める想定です。 具体的な原因の切り分けと修正方法の検討はAIに委ねるため、現時点では確定していません。

実装・検証レポートの分かりやすさを改善する

実装・検証レポートはビジュアルドキュメントとして作成していますが、人間が内容を把握しやすくする点では、まだ改善の余地があると認識しています。実務を進める中で、特に確認すべきポイントが明確になってくると考えているため、それに合わせて自動作成される報告書も改善していく予定です。
